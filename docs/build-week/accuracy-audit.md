# Phase 4C Accuracy and Trustworthiness Audit

Audit date: 2026-07-14

Base commit: `8bafcdd` plus the audit's fake-evidence clock correction

Scope: travel-facing schemas, prompts, provider boundaries, validators, decision logic, public projection, and automated cases. No fresh live provider or model call was made.

## Executive assessment

Trailie has strong structural safeguards: provider evidence has an explicit status and expiry, missing provider data remains unavailable/unknown, itinerary publication requires an application-computed PASS, approvals are version- and membership-scoped, and public output is a deterministic allowlisted projection. No code path was found that turns a model assertion into verified evidence or a booking.

Trust is not equivalent to comprehensive travel accuracy. The current live adapter verifies only Mapbox geocoding and drive/walk/bike route distance/duration. Place hours, reservations, transit/shuttle, weather, park alerts, daylight, lodging/flight availability, and live prices remain unavailable. Several validators use lexical matching or one itinerary timezone and have material false-positive/false-negative risk. The product is suitable for a bounded Preview with its disclaimers, but not for users to treat as an authoritative travel or booking source.

## Privacy and public accuracy

The public projection drops traveler identities/origins, coordinates, costs, evidence, notes, confirmation details, private constraints, and identifying statements. It retains general itinerary-level accessibility/dietary wording only when it does not identify a traveler. Public tokens are verified server-side against immutable plan and snapshot hashes; malformed, unknown, expired, revoked, and drifted states collapse to one response. Unit, pgTAP, and anonymous-browser E2E evidence support this boundary.

Residual risk remains because deterministic regular expressions are not a formal data-loss-prevention system. A production privacy review, adversarial corpus, logging review, and legal disclosure review are required before unrestricted public use.

## Accuracy blockers and required follow-up

1. Run live Mapbox geocode and route smoke in the hosted environment and verify token restriction, timeout, quota, stale, unavailable, and provider-failure states.
2. Add explicit UI provenance/status copy for routes, prices, reservations, availability, and last-checked time where users make decisions.
3. Add invalid-date, DST, multi-timezone, traveler-specific arrival/departure, accessibility, dietary, unknown-cost, and incomplete-provider mutation tests.
4. Expand or narrow lexical confirmed/rejected/constraint checks with a documented policy and adversarial evaluation set; do not represent these checks as semantic completeness.
5. Preserve “No bookings were made,” no live availability, and accuracy/availability disclaimers in Preview submission copy.

## Verdict

**Accuracy and trustworthiness: conditional for Preview, insufficient for unrestricted production.** Implemented evidence and publication boundaries are conservative and fail closed, but live provider breadth, travel-specific validator depth, provenance UX, and evaluated model/provider accuracy remain incomplete.

### Phase 5A hosted accuracy evidence

With Mapbox absent and no fake provider configured, generated route/coordinate facts remained unknown. Missing optional-provider evidence is now a medium unverified warning instead of a non-repairable publication block; overlaps and duplicates still require deterministic repair. A real hosted Version 1 required one repair and published only after validation `pass`. Traveler-name redaction removed a model-generated title and summary; generic privacy-safe headings now preserve public usability without restoring private names. Historical Version 1 stayed pinned after Version 2 and disappeared immediately after revocation.
